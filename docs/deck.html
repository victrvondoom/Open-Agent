PeoplePay-360 · PayProof

Proof-carrying commission dispute resolution. It works out what should have been paid, shows the evidence, tests the alternatives, and only then acts, with approval.

Synthetic data · simulated payroll adapter · Python stdlib + vanilla JS

Problem

“Why is my commission wrong?” has five different answers

CRM
$60,000 opportunity
Contract
amended to $50,000
Billing
partly paid, credit note, payment recorded late
Comp plan
collection basis, versioned rates, exceptions
Payroll
$3,600 paid, then the same clawback twice

Analysts reconcile this by hand. Chatbots guess. Neither leaves a proof, and neither is safe to let near payroll.

Target users: sales-compensation and payroll operations analysts, finance approvers, and the reps who file disputes.

How it reasons

An adversarial workflow with a deterministic verifier

Investigator→Skeptic→Policy verifier→Resolution planner→Final validator
Skeptic's strongest counterargument
Materiality, not vibes
Conflicting amendments are recomputed under each alternative. If the outcome changes the case is DISPUTED; if not, it is VERIFIED.
Model at the edge
Nemotron only phrases explanations. Any sentence with an unknown record id or an invented amount is dropped and counted.
Signature feature

Counterfactual payout replay

Same engine, hypothetical overlays, always labelled hypothetical and never treated as financial events.

Safe action

Approval gated, executed at most once, verified afterwards

PROPOSED→VALIDATED→AWAITING_APPROVAL→APPROVED→EXECUTED→VERIFIED
  • Backend authorization, approval limits ( for a finance approver, controller above), segregation of duties. The rep's own approval gets a 403.
  • Idempotency key and source fingerprint are re-checked at approval and at execution. Stale evidence moves the action to EXPIRED.
  • Postcondition: the case is re-investigated with the simulated ledger, so paid = and variance = $0. A hash-chained receipt is issued; a failed postcondition yields none.
  • Negative case: no contract means NEEDS_EVIDENCE, and the only action allowed is to request evidence.

How Zetaris and Meterless are used

Meterless World Model as the evidence backbone

1 · Evidence intake
Every source record is ingested with provenance (source system, recorded time) and bitemporal edges (validFrom = effective time).
2 · Verifier cross-check
The World Model's as-of-cutoff view must contain exactly the cash events the Decimal engine counted. Otherwise the proof is REJECTED.
3 · Context builder
The Nemotron prompt is built from the World Model neighbourhood of the disputed deal.
4 · Stale-evidence gate
Each action snapshots the World Model. If re-ingest reports changed=true at approval or execution, the action EXPIRES.

Zetaris: one fixed, validated SELECT per source system over the documented REST SQL route, with per-system provenance on every investigation.

What's unique: the bitemporal edges carry the core payroll distinction, value date versus recorded date. The engine's idempotency contract becomes a payroll safety control.

Technical stack

Small, reproducible, judge-runnable

Core
Python standard library only, decimal money, an event-sourced Meterless World Model, and a stdlib HTTP API
UI
Vanilla JS Decision Room, no build step, responsive
Data
Zetaris REST SQL or local synthetic fixtures (SAMPLE_MODE)
Model
NVIDIA Nemotron via OpenAI-compatible API, at most 2 calls per run, cached
Evidence
JSONL traces in logs/, 3 samples, tests, a -case benchmark, and dispute intake so any new case runs the full pipeline
